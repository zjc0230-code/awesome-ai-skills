# 技术文档写作规范

本文件提供技术文档的专门写作规范，应与基础规范（SKILL.md）结合使用。

**参考资料**：本规范参考阮一峰《中文技术文档的写作规范》
- GitHub：https://github.com/ruanyf/document-style-guide.git
- 许可证：公共领域（public domain）

## 适用范围

编写或编辑以下类型的技术文档时使用此规范：
- 项目文档（README、使用说明等）
- 技术教程
- API 文档
- 设计文档
- 软件手册
- 知识库文档

## 标题规范（技术文档专用）

### 技术文档标题原则

技术文档的标题应更注重清晰性和可导航性。

#### （1）层级连续性

一级标题下，不能直接出现三级标题。

示例：下面的文章结构，缺少二级标题。

```markdown
# 一级标题

### 三级标题
```

#### （2）避免孤立编号

标题要避免孤立编号（即同级标题只有一个）。

示例：下面的文章结构，`二级标题 A`只包含一个三级标题，完全可以省略`三级标题 A`。

```markdown
## 二级标题 A

### 三级标题 A

## 二级标题 B
```

#### （3）名称不重复

下级标题不重复上一级标题的名字。

示例：下面的文章结构，二级标题与下属的三级标题同名，建议避免。

```markdown
## 概述

### 概述
```

#### （4）限制四级标题

谨慎使用四级标题，尽量避免出现，保持层级的简单，防止出现过于复杂的章节。

如果三级标题下有并列性的内容，建议只使用项目列表（Item list）。

示例：下面的结构二要好于结构一。结构一适用的场景，主要是较长篇幅的内容。

```markdown
结构一

### 三级标题

#### 四级标题 A

#### 四级标题 B

#### 四级标题 C

结构二

### 三级标题

**（1）A**

**（2）B**

**（3）C**
```

## 文档体系规范

### 软件手册结构

软件手册是一部完整的书，建议采用下面的结构。

- **简介**（Introduction）：[必备] [文件] 提供对产品和文档本身的总体的、扼要的说明
- **快速上手**（Getting Started）：[可选] [文件] 如何最快速地使用产品
- **入门篇**（Basics）：[必备] [目录] 又称"使用篇"，提供初级的使用教程
  - **环境准备**（Prerequisite）：[必备] [文件] 软件使用需要满足的前置条件
  - **安装**（Installation）：[可选] [文件] 软件的安装方法
  - **设置**（Configuration）：[必备] [文件] 软件的设置
- **进阶篇**（Advanced）：[可选] [目录] 又称"开发篇"，提供中高级的开发教程
- **API**（Reference）：[可选] [目录|文件] 软件 API 的逐一介绍
- **FAQ**：[可选] [文件] 常见问题解答
- **附录**（Appendix）：[可选] [目录] 不属于教程本身、但对阅读教程有帮助的内容
  - **Glossary**：[可选] [文件] 名词解释
  - **Recipes**：[可选] [文件] 最佳实践
  - **Troubleshooting**：[可选] [文件] 故障处理
  - **ChangeLog**：[可选] [文件] 版本说明
  - **Feedback**：[可选] [文件] 反馈方式

下面是两个真实范例，可参考。

- [Redux 手册](https://redux.js.org/introduction/getting-started)
- [Atom 手册](http://flight-manual.atom.io/)

### 文件名规范

文档的文件名不得含有空格。

文件名必须使用半角字符，不得使用全角字符。这也意味着，中文不能用于文件名。

```
错误：名词解释.md

正确：glossary.md
```

文件名建议只使用小写字母，不使用大写字母。

```
错误：TroubleShooting.md

正确：troubleshooting.md
```

为了醒目，某些说明文件的文件名，可以使用大写字母，比如`README`、`LICENSE`。

文件名包含多个单词时，单词之间建议使用半角的连词线（`-`）分隔。

```
不佳：advanced_usage.md

正确：advanced-usage.md
```

## 技术文档专用要求

### 代码示例

- 代码示例应使用标准的代码块语法高亮
- 每个代码示例前应有简短的说明
- 代码示例应包含必要的注释
- 重要代码行应有行号标记（如果需要）

### API 文档

- 每个 API 应包含：功能说明、参数、返回值、示例代码
- 参数应说明类型、是否必填、默认值
- 返回值应说明数据结构和示例
- 应提供完整的代码示例

### 截图和图表

- 截图应清晰、完整、标注必要的信息
- 图表应有清晰的标题和图例
- 多步骤操作应使用序列图或流程图
- 使用外部图片时，需在图片下方或文末标明来源

### 版本说明

- ChangeLog 应按版本号倒序排列
- 每个版本应包含：版本号、发布日期、主要变更
- 变更分为：新增、修改、修复、移除
- 破坏性变更应特别标注

## 技术文档写作风格

### 准确性

- 技术术语应准确无误
- 版本号、参数名称等应精确
- 避免模糊表述，如"可能"、"也许"

### 可操作性

- 教程应可按步骤执行
- 命令应可直接复制粘贴
- 代码应可运行
- 应提供完整的环境要求

### 可读性

- 使用清晰的章节划分
- 重要信息应突出显示
- 使用列表而非长段落
- 适当使用加粗、斜体强调

### 可维护性

- 内容模块化，便于更新
- 避免重复内容
- 建立清晰的版本管理
- 定期更新过时信息
